🔴  Critical — Must Fix Before Merge
1. git config filter misclassifies mutating operations as read-only
electron/git-command-filter.ts → isContextuallyReadOnly() config branch

The config detection counts non-flag positional tokens and classifies as read-only when ≤1. This misses flag-based mutating operations where the destructive flag starts with -- and gets filtered out of the positional count:

CommandExpectedActual
git config --unset user.nameMUTATINGREAD-ONLY ✗
git config --unset-all user.nameMUTATINGREAD-ONLY ✗
git config --remove-section coreMUTATINGREAD-ONLY ✗
git config --rename-section old newMUTATINGMUTATING ✓

An agent could use git config --unset to silently delete config values (e.g. the push.autoSetupRemote setting this PR adds), breaking subsequent VCS operations.

Suggested Fix
Add an explicit mutating-flag check before the positional-count heuristic: 
const CONFIG_MUTATING_FLAGS = /--unset|--unset-all|--remove-section|--rename-section|--replace-all|--edit/;
if (CONFIG_MUTATING_FLAGS.test(rest)) return false;
2. ConnectExistingView shells out raw git via editor.exec
src/components/layout/remote-origin-views.tsx, lines ~290–298

When vcs.addRemote fails with "already exists", the fallback runs a raw shell command:

const escaped = trimmed.replace(/'/g, "'\\''");
await window.sero.editor.exec(workspaceId, `git remote set-url origin '${escaped}'`);

Three problems:

  • No auth env injection on host. editor.exec → hostExec does NOT inject GitHub auth env vars. If the workspace runs on the host (containers disabled), git operations won't authenticate — inconsistent with all other git operations that go through GitRunner.
  • Shell injection surface. The single-quote escaping is fragile against multi-byte edge cases. The pattern of building shell strings from user input is inherently risky vs. using array-based arg passing through GitRunner.run().
  • Bypasses VCS abstraction. VcsOps already has addRemote — it should also have setRemoteUrl that goes through GitRunner.run() with proper auth and array args.
Suggested Fix
Add setRemoteUrl(workspaceId, name, url) to VcsOps, expose it via IPC + preload, and call that instead of shelling out. One-line implementation:
async setRemoteUrl(wsId: string, name: string, url: string) {
  return this.runner.run(wsId, ['remote', 'set-url', name, url]);
}
3. Auth token leaks into every container exec — not just git
electron/github/auth-manager.ts → getAuthEnvVars() · electron/container/index.ts → exec()

The GIT_CONFIG_VALUE_2 env var (containing the Base64-encoded GitHub token) is injected into every container exec call because ContainerManager.exec() unconditionally calls getExtraEnvVars().

  • ls, cat, node script.js, etc. all run with the token in their environment
  • Any process inside the container can read GIT_CONFIG_VALUE_2 from /proc/self/environ
  • Agent-authored scripts running in the container could exfiltrate the token
  • The token is directly readable in Base64, whereas the previous GIT_ASKPASS=gh approach at least acted as an intermediary
Suggested Fix
Consider only injecting auth env vars for git/gh commands — add a needsAuth?: boolean parameter to exec(), or limit the getExtraEnvVars callback to only fire when the command starts with git or gh. Alternatively, accept this as a known trade-off and add a prominent security comment documenting the blast radius.

4. Git command filter bypassable via subshells and eval
electron/git-command-filter.ts

The segment splitter only handles &&, ||, ;, and |. These bypass the filter entirely:

CommandResult
echo $(git push origin main)Bypassed
eval "git push origin main"Bypassed
bash -c "git push origin main"Bypassed

This is the agent filter (not a user filter), so the LLM is unlikely to deliberately craft these. But it could stumble into them via tool output or copied shell snippets. Consider additionally blocking commands containing $(, backticks, eval, or bash -c.

electron/github/repo-ops.ts · src/components/layout/remote-origin-views.tsx

createRepo() doesn't verify the user is authenticated before shelling out to gh repo create. The user fills out the form, clicks "Create", waits for the full container round-trip, then gets a cryptic auth error.

The formatError handler catches it, but the UX is poor — check auth status upfront in the renderer before showing the create form, or at the start of createRepo().

6. Repo name defaults to workspace.id — may be invalid for GitHub
src/components/layout/remote-origin-views.tsx, line ~148

useState(workspace.id) pre-fills the repo name input. Workspace IDs can contain characters GitHub disallows (spaces, special chars). The server-side validates with /^[a-zA-Z0-9._-]+$/ but the user sees an invalid default, then gets an error on submit.

Suggested Fix
Sanitize the default: 
workspace.id.replace(/[^a-zA-Z0-9._-]/g, '-').replace(/-+/g, '-')
7. Host git identity cached for entire process lifetime
electron/container/lifecycle.ts

_hostGitIdentity is cached once and never invalidated. If the user changes git config --global user.name mid-session, all new containers still get the stale identity. Since Electron sessions can run for days, this is more than theoretical.

Consider a TTL (re-read every 5 minutes) or clearing the cache when a new workspace is created.
