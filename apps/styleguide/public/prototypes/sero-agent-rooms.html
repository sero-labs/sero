Agent Rooms — prototype

Sero Orchestrator gets a second mode. Workflow runs an LLM-authored step graph. Room creates a persistent Conductor-led team from one plain-language problem, and adapts that team while it works.

The generated blueprint is detailed. The confirmation the user approves is not. Everything that carries authority — team size, time, spend, access — is computed by application code from the validated blueprint the runtime will enforce. The planner writes prose only.

  • One question starts a Room. Spend, time and access are optional, and pre-filled from safe defaults.
  • Adjust is natural language first. Forms live behind Advanced settings, never in the default path.
  • Members are real persistent Pi sessions. They are inspectable through the Room, and never appear as ordinary chats.
  • The Conductor adapts the team, never its own authority. Anything that widens access, spend or team size stops for the user.

1 · Orchestrator — Workflows and Rooms

Rooms are a mode of the existing product, not a new app. The home surface keeps the cross-mode “Needs you” inbox, then presents the two ways to start work. Nothing about Workflow behaviour changes.

4 · The proposal — computed, not written

The four authority tiles are the consent surface. The planner supplies the title, the one-sentence approach and the role one-liners — nothing that carries authority. The warning appears because a member has GitHub write; it is a fixed mapping, not planner prose.

Why this team? Planner reasoning

Session fixation is cheap to misdiagnose and expensive to get wrong, so the first job is confirming it exists rather than assuming it. The fix itself touches two separate concerns — the login path and everything downstream that reads the old session — which is why the work splits across two implementers in separate branches instead of one agent making a wide change. A dedicated tester keeps the proof honest: the test has to fail on the current code before it is allowed to pass on the fix.

7 · Advanced settings — the complete blueprint

The right rail shows what the compact proposal will compute from these values — so an advanced edit visibly moves the consent summary, and the summary can never drift from the blueprint the runtime enforces.

8 · The live Room

Three regions: who is on the team and what state each one is in, what has actually happened, and the current Room brief. The two dividers resize the side regions and remember their positions. The activity region keeps a useful minimum width. Reload returns to this Room and its selected view. The shell back and forward controls move through Orchestrator views as well as apps. The brief is built by the coordinator from Room records after structural progress — it is not a transcript summary, and no member ever reads the whole Room history. The Conductor may add a short situation note, which is labelled as its own and cannot change any computed field.

11 · The Conductor changes the team

Two revisions, deliberately different. Adding a member inside the approved envelope is applied and recorded — it does not interrupt anyone, and the user can inspect or undo it. Replacing a member with one that needs access nobody currently has is not applied; it becomes an approval request. The boundary is the operating envelope, and it is enforced in runtime code, not by asking the Conductor to behave.
