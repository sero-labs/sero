Git app — prototype

The surface that does the work. One selection model, three columns, no modes. The left rail is what you can switch to; the middle column is what you're working on; the right is always a diff. The working tree is just the top of the history, so staging and browsing a past commit use the same two motions — pick a thing on the left of the middle column, read it on the right.

1 · Default — working tree selected

The middle column repeats the explorer panel's structure at a larger size: changes on top with the commit box pinned beneath them, history below, both scrolling independently. Same pattern, two surfaces — that repetition is the unification.

What changed from today. The bottom staging strip is gone — staging lives in the middle column where there's room for it. The 45%-wide inline DiffViewer is gone — the right column is DiffChangeset. The empty middle is gone, because the graph no longer has the window to itself. Ref chips are capped at 92px with an overflow count, so the commit message is never pushed off the row — compare the top row today, where the message is invisible. Branch names are middle-truncated, so six branches sharing a prefix are actually distinguishable, and a branch checked out in a worktree is marked WT rather than listed twice.

4 · Switching branch with uncommitted changes

The one moment a git UI can lose your work. Rather than blocking you or silently failing, it names the three real outcomes and picks the safe one by default. Bring them along is what Git does on its own when the change doesn't conflict; the other two are the escape hatches.

You have 8 changed files, 2 of them staged. Choose what happens to them.

Bring them along
Keep your changes in the working tree on the new branch. Fails safely if a change conflicts.
Stash them first
Set them aside on main. Restore later from Stashes in the rail.
Discard them
Throw the changes away. This cannot be undone.
Cancel Switch branch

Why a dialog and not a toast. This is the only place in the app where an action can destroy work, so it is the only place that interrupts. Everything else — staging, discarding a single file, committing — is reversible or scoped enough to just happen.
