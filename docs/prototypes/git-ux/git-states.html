Git app — the hard states

The three states the current app has nothing to say about. A git UI is judged on these, not on the happy path: a merge conflict, a repository with no commits, and a detached HEAD. All three reuse the layout already agreed — rail, working tree + diff on top, graph below — so none of them is a special screen you have to learn.

1 · Merge conflict

The app enters a mode it announces and can leave. The banner states what is happening and offers the only two ways out. Conflicted files get their own section above staged and unstaged, because nothing else can proceed until they're gone, and the count in the commit button counts down as you resolve them.

Decisions this state makes. Fetch, pull, push and PR are disabled, not hidden — you can see why they're unavailable. Abort merge sits in the banner, the only place it applies, rather than in a menu. Files are grouped by what you must do about them: conflicted, resolved, merged cleanly — so the list itself is the to-do list. The commit button is disabled with a count, not a vague error. And the graph shows the merge as a dashed, unfinished node with both parents visible, so the shape of what you're doing stays on screen.

2 · Repository with no commits

A fresh git init: an unborn branch, no history, no remote. Every pane says what it needs rather than showing an error, and the one action that matters — make the first commit — is the only one enabled.

The graph fills in from your first commit. Nothing to fetch, push or open a pull request against until then.

Decisions this state makes. The unborn branch is shown, not hidden — main exists as a name even with nothing on it, and saying so is less confusing than an empty rail. Publish to GitHub replaces Create pull request in the same slot, because that's the actual next step. Untracked files are a new status of their own rather than being mixed in with modified ones. And the graph explains itself instead of rendering an empty grid.

3 · Detached HEAD

You've checked out a commit rather than a branch. This is the state most likely to lose work silently, so it says plainly what will happen and offers the two ways out — keep this work by naming a branch here, or leave and go back to a branch.

Decisions this state makes. HEAD appears in the branch rail as its own entry rather than leaving the rail with nothing selected — the rail always answers "where am I". Committing is disabled with the reason attached, so you can't silently create an orphan. Push and PR are off; fetch stays on because it's harmless. And HEAD is marked on the graph in warning colour, distinct from any branch tag, so the position is visible rather than inferred.
