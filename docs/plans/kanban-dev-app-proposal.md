# Sero Kanban Dev App — High-Level Proposal

> Automated development experience where ideas become delivered features with
> high-level observability, parallel execution, and minimal human intervention.

## 1. What It Is

A Sero app (`pi-kanban-extension`) that presents a **Kanban board** as the
primary interface for managing development work. Each card on the board
represents a unit of work (feature, bug fix, refactor) that moves through
stages — from idea to delivered — with AI agents doing the heavy lifting.

```
┌─ Backlog ──────┬─ In Progress ───┬─ Review ────────┬─ Done ───────────┐
│                │                  │                 │                  │
│ ┌────────────┐ │ ┌────────────┐  │ ┌────────────┐  │ ┌────────────┐  │
│ │ Add OAuth  │ │ │ API rate   │  │ │ Refactor   │  │ │ Fix login  │  │
│ │ support    │ │ │ limiting   │  │ │ user store │  │ │ redirect   │  │
│ │            │ │ │ ▓▓▓▓░░ 65% │  │ │ PR #42     │  │ │ PR #38 ✓  │  │
│ │ 3 subtasks │ │ │ 2/4 agents │  │ │ Reviewing  │  │ │ Merged     │  │
│ └────────────┘ │ └────────────┘  │ └────────────┘  │ └────────────┘  │
│                │                  │                 │                  │
│ ┌────────────┐ │ ┌────────────┐  │                 │ ┌────────────┐  │
│ │ Dark mode  │ │ │ Add tests  │  │                 │ │ Update     │  │
│ │ toggle     │ │ │ for auth   │  │                 │ │ README     │  │
│ │            │ │ │ ▓▓▓▓▓░ 80% │  │                 │ │ PR #37 ✓  │  │
│ └────────────┘ │ └────────────┘  │                 │ └────────────┘  │
└────────────────┴──────────────────┴─────────────────┴──────────────────┘
```

The user's role shifts from **implementer** to **product manager**: define
what you want, prioritise it, and watch agents build it. Intervene only for
critical decisions (architecture choices, ambiguous requirements, approval
to merge).

## 2. Core Concepts

### Card (Unit of Work)

A card is the atomic unit on the board. It captures:

| Field | Description |
|-------|-------------|
| `title` | Short name ("Add OAuth support") |
| `description` | Natural language spec — the "what" and "why" |
| `acceptance` | Optional acceptance criteria (checklist) |
| `priority` | `critical` / `high` / `medium` / `low` |
| `column` | Current board position |
| `branch` | Git branch created for this card's work |
| `sessionId` | Sero session driving the work |
| `subtasks` | Breakdown generated by the planning agent |
| `prUrl` | Pull request URL once pushed |
| `checkpoint` | Last VCS checkpoint for safe rollback |

### Columns (Stages)

```
Backlog → Planning → In Progress → Review → Done
```

| Column | What happens |
|--------|-------------|
| **Backlog** | User adds ideas. No agent work yet. |
| **Planning** | A planning agent analyses the codebase, breaks the card into subtasks, proposes an approach, and estimates complexity. Waits for user approval before proceeding. |
| **In Progress** | Implementation agents execute subtasks in parallel (where possible). Real-time progress visible on the card. VCS checkpoints created per subtask. |
| **Review** | A reviewer agent reviews the diff, runs tests, checks types. Creates a PR via VCS. Card shows PR link and review status. |
| **Done** | PR approved and merged (or user marks complete). |

### Human Checkpoints

The system pauses and asks the user for input at defined points:

1. **After Planning** — "Here's how I'll implement this. Approve?"
2. **On Ambiguity** — "This requirement is unclear. Which approach?"
3. **Before PR** — "Implementation complete. Ready to open PR?"
4. **On Failure** — "Tests are failing after 2 retry attempts. Help?"

These use the existing **user-feedback** IPC pattern (questions appear in
the ChatPanel, answers flow back to the waiting agent).

## 3. How It Maps to Sero

### 3.1 Sero App (standard pattern)

Follows the exact pattern from `docs/apps-tutorial.md`:

```
packages/pi-kanban-extension/
├── package.json          # pi + sero manifest
├── shared/
│   └── types.ts          # KanbanState, Card, Subtask, Column
├── extension/
│   └── index.ts          # Pi extension: kanban tool + commands
├── ui/
│   ├── KanbanApp.tsx     # Board UI (React, module federation)
│   ├── components/       # Column, Card, CardDetail, SubtaskList
│   └── styles.css
└── vite.config.ts
```

- **State file**: `.sero/apps/kanban/state.json` (workspace-scoped)
- **`useAppState<KanbanState>`** for reactive UI updates
- **Pi extension** registers a `kanban` tool the agent can call to
  manipulate cards programmatically
- Works in Pi CLI too (manage cards via `/kanban` command)

### 3.2 Workspace = Project

Each workspace is already a bounded project context in Sero. The Kanban
board is workspace-scoped — your board for `sero-dev` is separate from
your board for `trading-bot`. This is automatic via the existing
`stateFile` mechanism.

### 3.3 Sessions = Card Workers

Each card in **In Progress** gets its own **Sero session**, bound to the
workspace. This leverages the existing `AgentPool` (AD-011) which already
supports multiple simultaneous `AgentSession` instances per workspace.

```
Workspace: sero-dev
├── Session: "Main chat" (user's interactive session)
├── Session: "Card: Add OAuth support" (agent working on card)
├── Session: "Card: API rate limiting" (agent working on card)
└── Session: "Card: Add tests for auth" (agent working on card)
```

The card's session runs autonomously with a system prompt constructed from:
- The card's description and acceptance criteria
- The planning agent's subtask breakdown
- Workspace context (from the existing composite environment)

### 3.4 Subagents = Parallel Subtask Execution

Within a card's session, the existing **subagent system** (AD-021) handles
parallel execution of independent subtasks:

```
Card Session: "Add OAuth support"
  ├── subagent(analyst): "Analyse existing auth module"
  ├── subagent(scout):   "Find OAuth libraries in use"
  │
  │   (results feed into planning)
  │
  ├── subagent(implementer): "Add Google OAuth provider"     ← parallel
  ├── subagent(implementer): "Add GitHub OAuth provider"     ← parallel
  ├── subagent(test-writer): "Write OAuth integration tests" ← parallel
  │
  │   (all complete → chain to review)
  │
  └── subagent(reviewer): "Review all OAuth changes"
```

This uses the existing single/parallel/chain modes. The Kanban app just
needs to **orchestrate the right sequence of subagent calls** via the
card session's system prompt and planning output.

### 3.5 VCS = Branch-Per-Card

The existing VCS system provides everything needed:

| VCS Feature | Kanban Usage |
|-------------|-------------|
| **Branches** (`VcsOps.createBookmark`) | Auto-create `feat/add-oauth-<id>` per card |
| **Checkpoints** (`VcsManager.createCheckpoint`) | Snapshot after each subtask completes |
| **Restore** (`VcsManager.restoreCheckpoint`) | Roll back a card's work if it goes wrong |
| **PR creation** (`VcsPullRequestOps.create`) | Auto-create PR when card moves to Review |
| **Push** (`VcsOps.push`) | Push the card's branch to remote |
| **Branch naming** (`branch-naming.ts`) | Already has `inferConventionalType` + `slugifyBranchLabel` |

The card session works on its own branch. The VCS checkpoint system provides
safe rollback points. When implementation is complete, the existing PR
creation flow opens a PR with the diff summary auto-generated.

### 3.6 CLI Integration

The Pi extension registers a `kanban` tool (bridged via `sero-cli` per
AD-020) with actions:

```
sero-cli kanban list                    # Show all cards
sero-cli kanban add "Add OAuth" --priority high
sero-cli kanban start <card-id>         # Move to Planning
sero-cli kanban approve <card-id>       # Approve plan, move to In Progress
sero-cli kanban status <card-id>        # Show progress + subtask status
sero-cli kanban pause <card-id>         # Pause execution
sero-cli kanban cancel <card-id>        # Cancel and clean up
```

### Key: The Orchestrator

The **KanbanOrchestrator** is the only significant new component on the
backend. It sits in `electron/kanban/` and reacts to state transitions:

```typescript
// Simplified flow
class KanbanOrchestrator {
  // Called when state.json changes
  async onCardTransition(card: Card, fromColumn: Column, toColumn: Column) {
    switch (toColumn) {
      case 'planning':
        await this.runPlanningPhase(card);
        break;
      case 'in-progress':
        await this.runImplementationPhase(card);
        break;
      case 'review':
        await this.runReviewPhase(card);
        break;
    }
  }

  private async runPlanningPhase(card: Card) {
    // 1. Create a session for this card
    // 2. Run analyst + scout subagents to understand the codebase
    // 3. Generate subtask breakdown
    // 4. Update card state with plan
    // 5. Ask user for approval (user-feedback pattern)
  }

  private async runImplementationPhase(card: Card) {
    // 1. Create branch: feat/<slug>-<id>
    // 2. For each subtask group (respecting dependencies):
    //    a. Fan out independent subtasks as parallel subagents
    //    b. Create VCS checkpoint after each completes
    // 3. Run tests
    // 4. If tests pass → move to review
    // 5. If tests fail → retry or ask user
  }

  private async runReviewPhase(card: Card) {
    // 1. Run reviewer subagent on the full diff
    // 2. Run test-writer to fill coverage gaps
    // 3. Push branch
    // 4. Create PR via VcsPullRequestOps
    // 5. Update card with PR URL
  }
}
```

## 5. State Shape

```typescript
// shared/types.ts

export type Column = 'backlog' | 'planning' | 'in-progress' | 'review' | 'done';
export type Priority = 'critical' | 'high' | 'medium' | 'low';
export type CardStatus = 'idle' | 'agent-working' | 'waiting-input' | 'paused' | 'failed';

export interface Subtask {
  id: string;
  title: string;
  description: string;
  status: 'pending' | 'in-progress' | 'completed' | 'failed';
  dependsOn: string[];           // IDs of subtasks that must complete first
  agentRunId?: string;           // Subagent entry ID (for progress tracking)
  checkpointId?: string;         // VCS checkpoint after completion
}

export interface Card {
  id: string;
  title: string;
  description: string;
  acceptance: string[];           // Acceptance criteria checklist
  priority: Priority;
  column: Column;
  status: CardStatus;
  branch?: string;                // Git branch name
  sessionId?: string;             // Sero session driving work
  subtasks: Subtask[];
  plan?: string;                  // Planning agent's proposed approach
  prUrl?: string;                 // Pull request URL
  prNumber?: number;
  lastCheckpoint?: string;        // Latest VCS checkpoint ID
  error?: string;                 // Last error message
  createdAt: string;              // ISO
  updatedAt: string;              // ISO
  completedAt?: string;           // ISO
}

export interface KanbanState {
  cards: Card[];
  nextId: number;
  settings: {
    autoAdvance: boolean;         // Auto-move cards through stages
    maxConcurrentCards: number;   // How many cards can be In Progress at once
    requireApproval: {
      plan: boolean;              // Pause after planning for approval
      pr: boolean;                // Pause before creating PR
    };
  };
}
```

## 6. What We Build vs What We Reuse

### Reuse (existing Sero/Pi infrastructure)

| Component | What we get for free |
|-----------|---------------------|
| **Sero App framework** | Package structure, state file, module federation, `useAppState`, tool bridging, auto-discovery |
| **AgentPool** | Multiple simultaneous sessions per workspace |
| **SubagentManager** | Parallel/chain execution, concurrency limits, progress tracking, abort cascade |
| **VcsManager** | Checkpoints, restore, diff |
| **VcsOps** | Branches, push, bookmarks |
| **VcsPullRequestOps** | PR preview, creation, existing-PR detection |
| **Branch naming** | `inferConventionalType`, `slugifyBranchLabel` |
| **User feedback** | Question/answer flow for human checkpoints |
| **OrchestrationPanel** | Subagent monitoring UI (already built) |
| **ChatPanel** | Session output viewing (just focus the card's session) |
| **AppStateManager** | File watching, atomic writes, IPC |
| **GitHub auth** | `gh` CLI integration for PR creation |
| **Container isolation** | All agent work sandboxed per workspace |
| **`@sero/ui`** | shadcn components for the board UI |
| **Notifications** | `sero:notify` EventBus for card status updates |

### Build (new)

| Component | Scope |
|-----------|-------|
| **KanbanOrchestrator** | State machine reacting to column transitions. ~300 LOC. |
| **`pi-kanban-extension`** | Standard Pi extension with `kanban` tool + `/kanban` command. ~200 LOC. |
| **Board UI** | React components: `KanbanApp`, `BoardView`, `ColumnView`, `CardView`, `CardDetail`, `SubtaskList`. Uses existing shadcn + `@sero/app-runtime`. ~400 LOC total across components. |
| **Agent definitions** | 2-3 new `.md` agent files: `planner.md`, `implementer.md`. Reviewer and analyst already exist. |
| **Card session prompt builder** | Constructs system prompts for card sessions from card data + plan. ~100 LOC. |

**Estimated new code: ~1,000 LOC** (plus agent `.md` templates). Everything
else is wiring existing systems together.

## 7. User Experience Walkthrough

### Creating a Card

1. User opens the Kanban app from the sidebar (or types `/kanban add "Add
   OAuth support" --priority high` in chat)
2. Card appears in **Backlog** column
3. User fills in description and acceptance criteria via the card detail
   panel (or via chat: "describe what OAuth support means")

### Starting Work

4. User drags card to **Planning** (or clicks "Start" or types
   `/kanban start <id>`)
5. A planning session spins up — analyst and scout subagents explore the
   codebase
6. Card shows a spinner. After ~30s, the plan appears:

   > **Proposed Plan:**
   > 1. Add `passport-google-oauth20` and `passport-github2` packages
   > 2. Create `src/auth/providers/` with Google and GitHub strategies
   > 3. Add OAuth callback routes to `src/routes/auth.ts`
   > 4. Update the login UI with social buttons
   > 5. Write integration tests
   >
   > **Estimated subtasks:** 5 (3 parallelisable)
   >
   > **Approve this plan?** [Approve] [Edit] [Cancel]

7. User approves → card moves to **In Progress**

### Autonomous Implementation

8. Agent creates branch `feat/add-oauth-support-a1b2c3d4`
9. Subtasks 1-3 run in parallel via subagents (independent file scope)
10. Card shows real-time progress: `▓▓▓░░░ 3/5 subtasks`
11. Each completed subtask creates a VCS checkpoint
12. Subtask 4 (UI changes) depends on subtask 2 → runs after
13. Subtask 5 (tests) runs last → chain mode
14. Tests pass → card auto-moves to **Review**

### Review & Delivery

15. Reviewer subagent analyses the full diff
16. Branch is pushed, PR created via `VcsPullRequestOps`
17. Card shows: `PR #42 — 12 files changed, +340 -28`
18. Notification: "OAuth support ready for review — PR #42"
19. User reviews PR on GitHub (or in Sero's future PR view)
20. User merges → marks card Done

### Error Recovery

At any point, if something goes wrong:
- **Test failure**: Agent retries with a fix. After 2 failures, pauses
  and asks the user.
- **Ambiguity**: Agent pauses, asks via user-feedback. Card shows
  "Waiting for input".
- **Crash/timeout**: Card stays in current column with error badge. User
  can retry or roll back to the last checkpoint.
- **User override**: User can always pause a card, take over manually
  in the chat, or drag it back to a previous column.

## 8. Observability

The board IS the observability layer. At a glance you see:

- **Which cards are active** and in which stage
- **Progress per card** (subtask completion %)
- **Agent activity** (click card → see subagent status via existing
  OrchestrationPanel)
- **Session logs** (click card → focus its session in ChatPanel)
- **VCS history** (click card → see checkpoints, diff, branch)
- **Cost tracking** (subagent costs from the existing tracker)
- **Errors and blocks** (red badges, "waiting for input" status)

Desktop notifications (via existing `sero:notify`) for:
- Card completed a stage
- Card needs user input
- Card failed and needs attention
- PR created

## 9. Phasing

### Phase 1: Static Board (Sero App)

Build the `pi-kanban-extension` as a standard Sero app:
- State file with cards and columns
- Pi extension with `kanban` tool (add, list, move, update, delete)
- Board UI with drag-and-drop between columns
- Card detail panel
- No automation — user manually moves cards

**Validates**: app framework integration, state shape, UI patterns.

### Phase 2: Planning Automation

- KanbanOrchestrator reacts to `backlog → planning` transition
- Spawns a planning session using analyst + scout subagents
- Generates subtask breakdown
- User approval gate before advancing

**Validates**: orchestrator pattern, agent-driven planning, user feedback.

### Phase 3: Implementation Automation

- KanbanOrchestrator handles `planning → in-progress`
- Branch creation per card
- Parallel subtask execution via subagents
- VCS checkpoints per subtask
- Progress tracking in UI
- Auto-advance to review on completion

**Validates**: full autonomous loop, VCS integration, parallel execution.

### Phase 4: Review & Delivery

- Reviewer subagent on diff
- Auto-push + PR creation
- Card shows PR status
- Completion flow

**Validates**: end-to-end delivery pipeline.

## 10. Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| Agents produce low-quality code | Reviewer subagent + test runner as gates. User approval at review stage. Checkpoints for rollback. |
| Parallel agents conflict on files | Planning phase assigns independent file scope per subtask. System prompt reinforces this. |
| Cost explosion from many concurrent agents | `maxConcurrentCards` setting. Subagent cost tracking visible on each card. Budget alerts in v2. |
| Long-running cards block workspace | Cards run in sessions, not the user's main session. User can chat and work normally. |
| Complex dependency chains between subtasks | Planning agent models dependencies. Chain mode for sequential work. Parallel only for truly independent tasks. |
| State file grows too large | Archive completed cards periodically. Keep only recent history in active state. |

## 11. Why This Design

**Minimal new code.** The entire backend is essentially a state machine
(KanbanOrchestrator) that calls existing Sero APIs. No new IPC channels,
no new stores, no new agent infrastructure. We're composing existing
building blocks:

- Sero App framework → board UI + state management
- AgentPool → card sessions
- SubagentManager → parallel subtask execution
- VCS → branching, checkpoints, PRs
- User feedback → human checkpoints
- Notifications → status updates

**The Kanban board is a UX layer on top of capabilities Sero already has.**
The difference is that today, a user has to orchestrate these manually
("create a branch, implement this, run tests, create a PR"). The Kanban
app automates the orchestration and gives the user a visual control
surface.
