### Create Domestic Payment Request (Python)

Source: https://developer.starlingbank.com/docs/pisp

This snippet demonstrates how to construct and send a request to create a domestic payment using the Starling Bank API. It includes generating a UUID for the external identifier and defining the payment recipient. Ensure you have the `requests` library installed.

```python
import requests
import uuid

base_url = "https://api.starlingbank.com/api/v2"
access_token = "YOUR_ACCESS_TOKEN"
account_uid = "YOUR_ACCOUNT_UID"
default_category_uid = "YOUR_DEFAULT_CATEGORY_UID"

headers = {
    "Authorization": f"Bearer {access_token}",
    "Content-Type": "application/json"
}

payment_data = {
    "externalIdentifier": str(uuid.uuid4()),
    "amount": {
        "currency": "GBP",
        "minorUnit": 1000  # Example: 10.00 GBP
    },
    "paymentRecipient": {
        "accountHolderName": "Jane Doe",
        "снаб": "GB29NWBK60161331926819" # Example IBAN
    },
    "reference": "Test Payment"
}

url = f"{base_url}/payments/local/account/{account_uid}/category/{default_category_uid}"

response = requests.put(url, headers=headers, json=payment_data)

if response.status_code == 202:
    print("Payment initiated successfully.")
    print(response.json())
else:
    print(f"Error initiating payment: {response.status_code}")
    print(response.json())

```

### Making Signed Requests

Source: https://developer.starlingbank.com/docs/index

This section details how to construct and sign requests to the API using your private API key. It covers the content to be signed, the signature format, and the complete request structure.

```APIDOC
## Making Signed Requests

### Description
This endpoint requires signed requests to authenticate and authorize your API calls. You will use your private API key to sign the request content, which includes the request URL, date, and request body.

### Method
All HTTP methods (e.g., PUT, POST, GET, DELETE)

### Endpoint
All API endpoints

### Parameters
#### Path Parameters
None

#### Query Parameters
None

#### Request Body
Depends on the specific API endpoint being called.

### Content to be Signed
The content to be signed is a structured string that includes:
- `(request-target)`: The HTTP method and path of the requested resource (e.g., `put /api/v2/payments/local/account/...`).
- `Date`: The ISO 8601 timestamp of the request (e.g., `2020-04-07T18:26:30.668978+01:00`). Requests must be made within 5 seconds of this timestamp.
- `Digest`: The SHA-512 digest of the request payload. Use `X` if there is no request body.
- Optional additional HTTP headers (e.g., `Content-Type`). These headers must also be present in the HTTP request.

**Example Content to be Signed:**
```
(request-target): put /api/v2/payments/local/account/bbbbbbbb-bbbb-4bbb-bbbb-bbbbbbbbbbbb/category/cccccccc-cccc-4ccc-cccc-cccccccccccc
Date: 2020-04-07T18:26:30.668978+01:00
Digest: Aw4ttuzY7Rn0ad4QFkauxuWrLbgBY3QhtYm8SCKDFY2FlmzKgsk5zwW4CJzdc/8hECqylyXaYyOZsH1/rq1qHQ==
```

### Signature Generation
1. Sign the content described above using your private API key and a supported algorithm (`rsa-sha256`, `rsa-sha512`, `ecdsa-sha256`, or `ecdsa-sha512`).
2. Encode the resulting signature in Base64.

### Authorization Header Format
The `Authorization` header must include the `Signature` field:
```
Signature keyid="<keyid>",algorithm="<algorithm>",headers="<headers>",signature="<signature>"
```
- `keyid`: The UID of your API key.
- `algorithm`: The signing algorithm used (e.g., `rsa-sha512`).
- `headers`: A space-delimited list of elements included in the content to be signed (e.g., `(request-target) Date Digest`).
- `signature`: The Base64 encoded signature.

```

### Complete Request
In addition to the `Authorization` header, the request must include the `Date` and `Digest` headers, and any other headers specified in the `headers` field of the `Signature`.

**Example cURL Request:**

### Receiving the Authorization Code

Source: https://developer.starlingbank.com/docs/index

This section describes how your application receives an authorization code at your specified redirect URI after a user has successfully authenticated and authorized your application.

```APIDOC
## Receiving the Authorization Code

### Description
Upon successful user authentication and authorization, Starling Bank redirects the user to your specified `redirect_uri`. This redirection includes an authorization `code` and the `state` parameter you initially provided.

### Method
N/A (This describes a redirect, not a direct API call)

### Endpoint
Your registered `redirect_uri`

### Parameters
#### Query Parameters
- **code** (string) - Required - A temporary authorization code that can be exchanged for an access token. This code expires shortly after issuance.
- **state** (string) - Required - The `state` value that was sent in the initial authorization request. It is crucial to verify that this matches the original `state` value.

### Request Example
```
https://your.application.url/redirect/path?code=edv79CsZn80frhfxgF4o58aXAc7enpgB1wyv&state=249a34c4-4588-449a-9ad9-f192581e52fd
```

### Response
#### Success Response (Redirect)
- **code** (string) - The authorization code.
- **state** (string) - The state parameter.

#### Response Example
(See Request Example above, as the response is part of the redirect URL)
```

### V2 Webhooks

Source: https://developer.starlingbank.com/docs/index

Register for V2 webhooks to receive real-time notifications about feed item events (transactions, withdrawals, direct debits) and standing order events. V2 webhooks use public-private key pairs for enhanced security.

```APIDOC
## V2 Webhooks

### Description
Allows registration for event notifications such as card transactions, cash withdrawals, direct debit payments, and standing order events. V2 webhooks provide more event data in the payload compared to V1 and use public-private key cryptography for security.

### Usage
- Create personal access token webhooks for your own account notifications.
- Create application webhooks (sandbox and production) for your application users' account notifications.

### Security
V2 webhooks use a public-private key pair. Starling Bank creates a key pair when you create a webhook. They use the private key to sign event notifications, and you use the provided public key to verify the signature.

### Specifications
Refer to the end of the API reference documentation for detailed V2 webhook specifications.
```

### Access Tokens and Access Scopes

Source: https://developer.starlingbank.com/docs/index

Explanation of how access tokens and OAuth scopes control access to API endpoints. Details on obtaining tokens and scopes for personal use versus TPP usage.

```APIDOC
## Access Tokens and Access Scopes

Each access token grants access to a single customer account and is associated with one or more OAuth scopes. These scopes dictate which API endpoints your token can access.

To call an endpoint, you must supply a valid access token for the relevant account with the required scope.

**Example**: To call `GET /api/v2/accounts/{accountUid}/balance`, you need an access token with the `balance:read` scope for that account.

*   **Personal Use**: Create a personal access token in the Developer Portal and select the necessary scopes.
*   **Regulated TPPs**: Scopes are determined by regulatory approval.
```

### Payment Reviews

Source: https://developer.starlingbank.com/docs/pisp

Details on how payment requests might be reviewed, affecting payment status and potential actions.

```APIDOC
## Payment Reviews

### Description
Under certain circumstances, payment requests may be subject to a review process which can take a few hours. This can lead to payments remaining in a pending state for longer or eventual rejection. Sandbox payments are not subject to review.

### Endpoints Involved
- **PUT `/api/v2/payments/local/account/{accountUid}/category/{categoryUid}`**: Make a one-off payment to a new payee.
- **PUT `/api/v2/payments/local/account/{accountUid}/category/{categoryUid}/standing-orders`**: Create a new standing order to a new payee.
- **GET `/api/v2/payments/local/payment-order/{paymentOrderUid}/payments`**: Check the status of a one-off payment.
- **GET `/api/v2/payments/local/account/{accountUid}/category/{categoryUid}/standing-orders/{paymentOrderUid}`**: Check the status of a standing order.
- **DELETE `/api/v2/payments/local/account/{accountUid}/category/{categoryUid}/standing-orders/{paymentOrderUid}`**: Cancel a standing order.

### Status Indicators
- **One-off Payment**: If pending, `GET /api/v2/payments/local/payment-order/{paymentOrderUid}/payments` returns `paymentStatusDetails.paymentStatus = PENDING`. If rejected, it returns `paymentStatusDetails.paymentStatus = REJECTED`.
- **Standing Order Creation**: If pending, `GET /api/v2/payments/local/account/{accountUid}/category/{categoryUid}/standing-orders/{paymentOrderUid}` returns a null `startDate`. If rejected or cancelled, it returns a non-null `cancelledAt`.

### Actions During Pending Review (Standing Orders)
If a standing order creation request is pending, you will receive a `400` error if you attempt to:
- Call `DELETE /api/v2/payments/local/account/{accountUid}/category/{categoryUid}/standing-orders/{paymentOrderUid}` to cancel it.
- Call `PUT /api/v2/payments/local/account/{accountUid}/category/{categoryUid}/standing-orders/{paymentOrderUid}` to modify it.
```

### Generate UUID for External Identifier (JavaScript)

Source: https://developer.starlingbank.com/docs/pisp

This JavaScript snippet shows how to generate a Universally Unique Identifier (UUID) which is required for the `externalIdentifier` field when creating a payment. This utilizes the built-in `crypto` module in Node.js or can be adapted for browser environments.

```javascript
function generateExternalIdentifier() {
  // For Node.js environment
  if (typeof require !== 'undefined') {
    const crypto = require('crypto');
    return crypto.randomUUID();
  }
  // For browser environment (requires polyfill or modern browser support)
  else if (window.crypto && window.crypto.randomUUID) {
    return window.crypto.randomUUID();
  }
  // Fallback for older environments (less secure, not recommended)
  else {
    return 'xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx'.replace(/[xy]/g, function(c) {
      var r = Math.random() * 16 | 0, v = c == 'x' ? r : (r & 0x3 | 0x8);
      return v.toString(16);
    });
  }
}

const externalId = generateExternalIdentifier();
console.log("Generated External Identifier:", externalId);

```

### OAuth 2.0 Authentication Flow

Source: https://developer.starlingbank.com/docs/index

Starling uses OAuth2 to authenticate and authorize requests to its API. This process allows users to grant your application access to their Starling Bank account data without sharing their credentials.

```APIDOC
## OAuth 2.0 Authentication Flow

Starling uses OAuth2 to authenticate and authorise requests to our API. This allows Starling Bank account holders to authorise your application to access their data, without handing over their Starling credentials.

### Flow Steps

1.  **Redirect User to Starling**: Direct the user to Starling's authorization page.
2.  **User Authentication and Authorization**: Starling authenticates the user, who then authorizes your application.
3.  **Redirect Back to Application**: Starling redirects the user back to your application with an authorization code.
4.  **Exchange Code for Tokens**: Exchange the authorization code for an access token and a refresh token. This request must be secured with your OBIE or eIDAS certificate.
5.  **Use Starling API**: Use the Starling API with the access token included in every request.
6.  **Refresh Access Token**: Use the refresh token to obtain new access and refresh tokens. This request also requires your OBIE or eIDAS certificate.

### Personal Access Tokens

If you have a Starling Bank account and want to access your own account data, you can create a personal access token in the Developer Portal. You can then skip to step 5 and use the Starling API directly with your personal access token. Personal access tokens do not expire.

### Redirecting to Starling

Initiate the authentication process by redirecting the user to the Starling OAuth page.

*   **Sandbox**: `https://oauth-sandbox.starlingbank.com`
*   **Production**: `https://oauth.starlingbank.com`

#### Optional Parameters

*   **`redirect_uri`**: (Optional) The URI to which Starling will redirect the user after authorization. If omitted, the default redirect URI registered in the Developer Portal is used. If provided, it must match the default URI or be a sub-resource of it.
*   **`scope`**: (Optional) A space-separated list of access scopes your application requires (spaces encoded as `%20`). You can only request scopes previously approved for your application. If omitted, all approved scopes are granted.

#### Query Parameters

*   **`client_id`** (string) - Required - Your application's client ID.
*   **`response_type`** (string) - Required - Must be set to `code`.
*   **`state`** (string) - Required - An unpredictable, randomized string to protect against cross-site request forgery.
*   **`redirect_uri`** (string) - Optional - The URI to redirect the user to after authorization.
*   **`scope`** (string) - Optional - A space-separated list of requested scopes.

#### Example OAuth URI

```
https://oauth.starlingbank.com/?client_id=aT6TPtsTJvhB1wzGbrRp&response_type=code&state=249a34c4-4588-449a-9ad9-f192581e52fd&redirect_uri=https://your.application.url/redirect/path&scope=account-list:read%20confirmation-of-funds:read
```
