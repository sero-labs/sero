# PR lifecycle — 60-second demo

## Hook

I let Sero watch a pull request and keep it moving: CI goes red, Sero fixes it on the PR's own branch, and I still merge.

## Honest caveats

- **Real durations (the demo is not real-time).** GitHub is polled on an interval — default 2 minutes, 60-second floor — so event pickup adds up to ~2 minutes. CI itself runs for minutes, and the fix is a genuine background-agent run (30-minute cap, typically several minutes). The 0:20–0:28, 0:28–0:40, and 0:49–0:55 beats are timelapses, not real-time footage.
- **Required setup.** `gh` CLI signed in (`gh auth login`); a GitHub repo added as a Sero workspace with CI configured and an **open PR you (or Sero) authored**; the CI fixer loop installed from the catalog and **activated**; a model connected (hosted API key or a local OpenAI-compatible server). The loop is off until you activate it.
- **Approval and review posture — read this before the "gate" question comes up.** A visible Approve/Reject gate is the *typical, intended* path for a loop that acts outside your machine, and most demos should show it. This workflow deliberately does not: for a Pull request delivery there is **no pre-send approval popup** — once a run reaches its final step, the push and the PR comment happen autonomously, by design, because the PR itself is the review surface. That no-approval choice is valid, not a gap: your control points are the ones the demo shows — the loop does nothing until you click **Activate**; it acts only on open PRs you or Sero authored; it runs in an isolated managed worktree checked out on the PR's own branch (never your working tree, never `main`); it never merges and never opens a new PR; and you read the pushed commit and comment before merging, like a teammate's PR. The pre-send Approve/Reject question exists for **externally-visible** destinations — send email, chat post, webhook POST — which this loop never uses. So for this demo, tell the honest story (activation consent + isolation + never-merges + review-on-PR); do not stage a fake approval dialog for the PR push.
- **Beta rough edges.** Event pickup rides GitHub's list-endpoint polling and can lag or back off under rate limits (the source-health chip shows this). Eligibility ("your PRs only") is judged by the model from the event context, so confirm the run acted on the PR you expect. A run can end `blocked` — for example if the failure won't reproduce locally or the failed checks can't be run in the worktree — and that outcome is surfaced in Attempt history rather than silently dropped, so don't film a take that assumes every run pushes a fix.
- **Review-response variant.** The same lifecycle has a sibling loop, **Review responder** (`github:review-comment`, batched on a 5-minute quiet period, delivery → Pull request), which works unaddressed review comments, pushes to the PR branch, and replies on each comment. It carries the same isolation and never-merge posture; swap it in if the demo repo is better suited to a review thread than a CI failure.
